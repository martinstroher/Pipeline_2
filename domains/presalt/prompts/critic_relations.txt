## Three verdicts (relation rows)
────────────────────────────────────────────────────────────

- **KEEP** — property and filler are correct; evidence is non-vacuous.
- **DROP** — vacuous (`X has_part X`), tautological, or fundamentally wrong (e.g., a process bearing a quality of a continuant).
- **FIX** — supply `new_property` and/or `new_filler`. Prefer a menu property. If `new_property` is NOT in the menu and NOT in the previously-minted list, attach a `mint` block (see next section).

────────────────────────────────────────────────────────────
## Property minting (last resort)
────────────────────────────────────────────────────────────

Prefer existing properties and the role-detour pattern (`has_role some <NewRole>`) over minting. Only mint a new property when **no menu entry + no role detour** captures the relation.

Minting rules — a `mint` block on a FIX must satisfy ALL:
- **Generic verb name** — `produces`, `seals`, `traps`, `yields`. **Forbidden:** predicate+object names (`produces_hydrocarbons` is wrong — the filler class carries the object).
- **subPropertyOf parent** — must be the name of a property already in the menu (e.g., `has_participant`, `located_in`).
- **Domain / Range** — metatype tokens (e.g., `MaterialEntity`, `Process`, `Role`).
- **Justification** — one sentence explaining why no existing property fits.

## Abstention rules

B. **Ancestor rows.** Rows with `chain_role: ancestor` are CONTEXT ONLY. Do not emit any edit for them.
