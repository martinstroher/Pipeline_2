## 4. Edge Cases and Failure Modes

### 4.1 Patterns That Will Fail or Produce Ambiguous Results

| Pattern | Problem | Mitigation |
|---------|---------|------------|
| **"associated with X"** | Too vague — no specific OWL property maps to "association" | Rule 5 exclusion. LLM should return empty relations for this phrase. |
| **"serves as X" / "acts as X"** | Dispositional/functional, not a formal relation | Rule 5 exclusion. These describe roles (BFO dispositions), not object properties. |
| **"X such as A, B, C"** | Enumeration — should these all be fillers of has_part? | Yes, if the pattern is "composed of X such as A, B, C". Extract the specific items (A, B, C) as fillers, not X. |
| **Process involving another process** | "involves X" where X is also a process → has_part vs has_participant ambiguity | Add explicit sub-rule: process-process → `has_part`; process-continuant → `has_participant`. |
| **Geological Structure inheres_in** | BFO says `inheres_in` applies to SDCs, but GeoCore models Geological Structure as a GDC | Accept `inheres_in` at reduced confidence (0.8). Note in code: GeoCore's modeling of Geological Structure as GDC is debatable — many geological structures behave as SDCs. |
| **Passive voice differentia** | "formed by X" — straightforward. "in which X occurs" — reversed subject/object | LLM must parse grammatical roles carefully. Include passive-voice examples in few-shot section if hallucination occurs. |
| **Multi-sentence NLDs** | Second/third sentences may contain relations not in the differentia | The prompt says "extract from differentia AND elaboration sentences" — this is intentional. Second sentences often contain crucial domain relations. |
| **Named individuals** | "Santos Basin Pre-Salt sequence" — instance, not a class | Relation extraction still applies: an individual can have `part_of`, `occurs_in`, etc. The `filler_source` should be `"domain_term"` if the basin is a domain term. |
| **Negation** | "lacking mud matrix" (Grainstone) | Negative existential restrictions (`not (has_part some MudMatrix)`) are beyond scope for this prompt. Don't extract. |
| **Circular fillers** | "Porosity is... defined as the ratio of void space to total rock volume" — void space is defined in terms of porosity | Both terms exist independently. Extract `inheres_in rock`. Don't extract void space as a `has_part` of porosity — it's a definitional component of the measurement, not a mereological part. |

### 4.2 Ambiguity Resolution Heuristics (Add to Prompt if Needed)

```
DISAMBIGUATION RULES (apply when multiple properties seem possible):
- "involves [continuant]" → has_participant
- "involves [process]" → has_part (process parthood)
- "formed by [process]" → generated_by
- "formed from [material]" → derives_from
- "property of [entity]" → inheres_in (subject must be a quality)
- "composed of [material]" → has_part
- "occurs in [place/entity]" → occurs_in (subject must be a process)
```

## 5. Batching Strategy: Category-Based Batches

**Recommendation: Process by category batch.** Reasons:

### Why Category Batching Is Optimal

1. **Category constrains expected property types** — the prompt includes category-aware guidance ("qualities MUST have `inheres_in`", "processes → look for `has_participant`"). This dramatically reduces hallucination because the LLM isn't guessing the term's ontological type — it knows.

2. **Filler resolution benefits from co-located terms** — terms in the same category often reference each other. "Porosity" and "permeability" are both quality terms; "calcite" and "dolomite" are both Earth Materials. Seeing the full category cohort helps the LLM resolve fillers against `known_terms`.

3. **Consistent with existing pipeline architecture** — the taxonomy builder already processes by category. Reusing this grouping avoids architectural divergence.

4. **Token budget management** — 186 terms at ~100 tokens/NLD = ~18,600 input tokens just for NLDs, plus the property vocabulary, upper classes, and known terms list. That's manageable for Gemini 2.5 Pro's context window in a single call, BUT:
   - A single call means a single point of failure
   - JSON output reliability degrades with array length
   - No possibility for category-specific instructions

5. **Error isolation** — if one category's extraction fails (JSON parse error, etc.), only that batch needs retry. Your existing checkpoint pattern handles this.

### Recommended Batch Sizes

| Category Size | Strategy |
|---------------|----------|
| ≤ 30 terms | Single batch |
| 31–60 terms | 2 batches of ~equal size |
| > 60 terms | Split into batches of ~25 |

For 186 terms across ~15 categories, most categories will be single-batch (< 30 terms each).

### Why NOT All-at-Once

- JSON output reliability: Gemini's structured output is measurably more reliable for arrays of ≤ 30 objects than for arrays of 186
- No category-specific guidance possible
- Single point of failure for entire extraction
- No checkpoint granularity

## 6. Handling Filler Resolution: Domain Terms vs. Upper Ontology

### The Three-Tier Filler Resolution Strategy

```
┌─────────────────┐     ┌──────────────────┐     ┌──────────────┐
│  domain_term    │ ──► │  upper_ontology   │ ──► │  external    │
│  (~186 terms)   │     │  (BFO/GeoCore/GR) │     │  (new concept)│
└─────────────────┘     └──────────────────┘     └──────────────┘
   Priority 1              Priority 2               Priority 3
```

**In the prompt itself:** pass both lists (known terms + upper classes) so the LLM can resolve against them. The LLM classifies each filler into one of three sources.

### Downstream OWL Encoding (for `owl_exporter.py`)

The three filler sources determine how the axiom is serialized in OWL:

#### (a) Both subject and filler are domain terms
```turtle
presalt:Dolomitization rdfs:subClassOf [
    a owl:Restriction ;
    owl:onProperty bfo:BFO_0000057 ;     # has_participant
    owl:someValuesFrom presalt:Calcite
] .
```
Both IRIs are in the `presalt:` namespace. These are the strongest, most valuable axioms — they create cross-links within the domain ontology.

#### (b) Filler is an upper-ontology class
```turtle
presalt:Porosity rdfs:subClassOf [
    a owl:Restriction ;
    owl:onProperty ro:RO_0000052 ;        # inheres_in
    owl:someValuesFrom geocore:GEOCORE_0000008  # Rock
] .
```
The filler IRI comes from the `UPPER_IRIS` mapping (already in your codebase). These axioms anchor domain terms to the upper ontology — ontologically important but less novel.

#### (c) Filler is external (not in any vocabulary)
Two options:

**Option A (recommended): Mint a new presalt: class with minimal annotation**
```turtle
presalt:MetabolicActivity a owl:Class ;
    rdfs:label "metabolic activity"@en .

presalt:Microbialite rdfs:subClassOf [
    a owl:Restriction ;
    owl:onProperty presalt:generated_by ;
    owl:someValuesFrom presalt:MetabolicActivity
] .
```

**Option B: Skip external fillers entirely**
Only encode axioms where both subject and filler are known. Simpler, but loses information.

**Recommendation:** Option A, but flag external fillers in the CSV output (column `Filler_Source`) so they can be reviewed before OWL export. A human or automated post-filter can decide which external concepts to mint vs. skip.

### Implementation: Known Terms List Construction

```python
# Build known_terms from the filtered terms CSV (Step 3 output)
known_terms = set(df_filtered["Readable_Term"].str.lower().tolist())

# Build upper_classes from UPPER_IRIS keys

```

Pass both to the prompt as formatted lists. The LLM resolves each filler against these lists. In post-processing, validate:
- If `filler_source == "domain_term"`, assert `filler.lower() in known_terms`
- If `filler_source == "upper_ontology"`, assert `filler.lower() in {k.lower() for k in upper_classes}`
- If validation fails, downgrade to `"external"` and log a warning

```python
    # Build NLD lookup
    nld_map = dict(zip(df_nld["Term"], df_nld["NLD"]))
    known_terms = sorted(df_nld["Term"].str.lower().unique())
    upper_classes = sorted(UPPER_IRIS.keys())

    # Format reference lists for prompt
    known_terms_str = ", ".join(f'"{t}"' for t in known_terms)
    upper_classes_str = ", ".join(f'"{c}"' for c in upper_classes)

    all_rows = []
    categories = df_cat["Category"].unique()

    for category in tqdm(categories, desc="Relation extraction"):
        cat_terms = df_cat[df_cat["Category"] == category]["Term"].tolist()
        batch = []
        for term in cat_terms:
            nld = nld_map.get(term, "")
            if nld:
                batch.append({"term": term, "nld": nld})

        if not batch:
            continue

        prompt = _RE_PROMPT_TEMPLATE.format(
            upper_classes=upper_classes_str,
            known_terms=known_terms_str,
            category=category,
            json_batch=json.dumps(batch, indent=2),
        )

        try:
            response_text = generate(
                prompt,
                model=model_name,
                system_instruction=_RE_SYSTEM_INSTRUCTION,
                temperature=temperature,
                response_mime_type="application/json",
            )
            results = json.loads(response_text)

            for item in results:
                term = item["term"]
                for rel in item.get("relations", []):
                    prop = rel.get("property", "")
                    if prop not in ALLOWED_PROPERTIES:
                        log.warn(f"Unknown property '{prop}' for '{term}' — skipping")
                        continue
                    if rel.get("confidence", 0) < 0.6:
                        continue
                    all_rows.append({
                        "Term": term,
                        "Category": category,
                        "Property": prop,
                        "Property_IRI": PROPERTY_IRIS.get(prop, prop),
                        "Filler": rel.get("filler", ""),
                        "Filler_Source": rel.get("filler_source", "external"),
                        "Confidence": rel.get("confidence", 0.0),
                        "Evidence": rel.get("evidence", ""),
                    })
        except Exception as e:
            log.error(f"Relation extraction failed for '{category}': {e}")

    df_out = pd.DataFrame(all_rows)
    if output_path is None:
        output_path = categorized_csv.replace("5_categorized", "6b_relations")
    df_out.to_csv(output_path, index=False, encoding="utf-8-sig")
    log.success(f"Relations extracted: {len(df_out)} axioms from {len(categories)} categories → {output_path}")
    return output_path
```

## 8. Prompt Refinement Checklist

Before deploying, validate with a pilot run on ~20 terms:

- [ ] **Batch size alignment:** `len(output) == len(input)` for every batch
- [ ] **Property vocabulary compliance:** no invented properties
- [ ] **Filler resolution accuracy:** spot-check domain_term fillers against known_terms
- [ ] **Empty relations acceptance:** some categories (site, Sedimentary Environment) should yield mostly empty
- [ ] **Confidence distribution:** if everything is 1.0, the LLM is overconfident — adjust prompt
- [ ] **Evidence quality:** evidence strings should be actual NLD substrings, not fabrications
- [ ] **No IS-A leakage:** the genus (Y in "X is a Y that Z") should NOT appear as a relation
- [ ] **Process-process vs process-continuant:** verify `has_part` vs `has_participant` disambiguation
- [ ] **External fillers ratio:** if > 40% of fillers are external, the known_terms list may be too narrow

## 9. Recommended Iteration Path

1. **Pilot:** Run on 2-3 categories (one process-heavy, one material-heavy, one quality) with the prompt above
2. **Evaluate:** Manual inspection of ~50 extracted axioms against NLDs
3. **Calibrate:** Adjust confidence thresholds, add/remove disambiguation rules
4. **Full run:** All categories
5. **OWL integration:** Extend `owl_exporter.py` to read `6b_relations.csv` and emit `owl:Restriction` axioms
6. **Verify:** Run OOPS! on the enriched ontology — check for new pitfalls introduced by object properties
